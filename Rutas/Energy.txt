# Inventario técnico - energy-monitoring-service

## 1. Identificación
- Servicio: `energy-monitoring-service` (también expuesto en FastAPI/health como `Microservice-Energy-Monitoring-Service`)
- Lenguaje/framework: Python 3 + FastAPI + Uvicorn
- Archivo principal: `main.py`
- Archivos de rutas/controladores: `main.py`, `monitoring/interfaces/rest/controllers/health_controller.py`, `monitoring/interfaces/rest/controllers/energy_simulation_controller.py`, `monitoring/interfaces/rest/controllers/energy_reading_controller.py`, `monitoring/interfaces/rest/controllers/device_consumption_controller.py`, `monitoring/interfaces/rest/controllers/consumption_alert_controller.py`, `monitoring/interfaces/rest/controllers/energy_meter_controller.py`
- Archivos de configuración: `monitoring/infrastructure/configuration/settings.py`, `monitoring/infrastructure/configuration/config_service_client.py`, `.env`, `.env.example`, `Dockerfile`, `docker-compose.yml`

## 2. HTTP / Red
- Puerto real: `8001` (fuente local actual: `.env` y `docker-compose.yml`)
- Puerto por defecto: `8080` (`settings.py` y `Dockerfile`)
- Variable de puerto: `PORT` / `APP_PORT` (en este repo local se usa realmente `APP_PORT=8001`; el código acepta ambas)
- Host: `0.0.0.0`
- Prefix/base path: `/api/v1`
- Health endpoints: `GET /api/v1/health`
- CORS: Habilitado. `allow_origins` desde `CORS_ALLOW_ORIGINS`; valor local actual `http://localhost:3000,http://localhost:5173`; `allow_credentials=True`; `allow_methods=["*"]`; `allow_headers=["*"]`

## 8. Inconsistencias internas encontradas
- Puerto inconsistente: `settings.py` y `Dockerfile` usan default `8080`, pero `.env` y `docker-compose.yml` usan `8001`. El puerto real local actual parece `8001`.
- Variable de puerto inconsistente: el código prioriza `PORT` sobre `APP_PORT`, pero el repo local usa `APP_PORT`; el `Dockerfile` usa `PORT`.
- Bootstrap Kafka inconsistente: `.env` usa `localhost:9092`, `.env.example` usa `localhost:29092`, `docker-compose.yml` usa `kafka:9092`.
- `.env` no define topics que sí usa el código: `KAFKA_TOPIC_DEVICE_REGISTERED`, `KAFKA_TOPIC_ENERGY_CONSUMPTION_RECORDED`, `KAFKA_TOPIC_ENERGY_READING_CREATED`. En local actual esos quedan resueltos por default de `settings.py` o por Config Service si existiera.
- Hay topic legacy todavía publicado: `energy.reading.created`.
- Hay aliases legacy de variables Kafka todavía soportados: `KAFKA_TOPIC_READING_INGEST`, `KAFKA_TOPIC_ANOMALY_DETECTED`, `KAFKA_TOPIC_ALERT_CREATED`, `KAFKA_TOPIC_READING_PROCESSED`, `KAFKA_USERNAME`, `KAFKA_PASSWORD`.
- `docker-compose.yml` crea topics hardcodeados que coinciden con defaults/.env.example, pero no con lo declarado completamente en `.env`.
- El microservicio tiene endpoint real de health `GET /api/v1/health`, pero `Dockerfile` no define `HEALTHCHECK` y `docker-compose.yml` no define healthcheck para este servicio.
- Los consumers sí están registrados y conectados, pero dos handlers están incompletos funcionalmente: `_handle_reading_ingest` y `_handle_anomaly_detected` solo loguean y tienen `TODO` para despachar lógica de aplicación.
- No encontré endpoints definidos fuera del router ni handlers REST desconectados del registro principal.
- No encontré publishers definidos pero totalmente sin uso.
- No encontré topics duplicados efectivos; `settings.get_kafka_topics()` además deduplica internamente.
