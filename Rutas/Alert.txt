## 8. Inconsistencias internas encontradas
- Puerto inconsistente: `.env` usa `SERVER_PORT=8085`, pero `.env.example`, `Dockerfile`, default de código y `docker-compose.yml` apuntan a `8080`.
- Prioridad de variables de puerto: el código prioriza `PORT` sobre `SERVER_PORT`; en `.env` solo existe `SERVER_PORT`, pero en Docker Compose se inyecta `PORT=8080`, por lo que local y contenedor no coinciden.
- `CONFIG_SERVICE_URL=http://localhost:8090` está activo en `.env`; este micro puede sobrescribir puerto/topics/brokers desde una fuente externa, pero esa configuración no está visible aquí.
- Health check inconsistente/incompleto: el código expone `/api/v1/health`, pero `Dockerfile` no define `HEALTHCHECK` y `docker-compose.yml` no define healthcheck para `alert-service`.
- Topics de consumo definidos por código no coinciden con `.env` local: aunque `.env` solo declara `energy.consumption.recorded`, `config.go` fuerza además `energy.reading.created` y `analytics.anomaly.detected`.
- Legacy Kafka duplicado: `KAFKA_CONSUMPTION_TOPIC` y `KAFKA_TOPIC_DEVICE_READING_CREATED` cumplen el mismo rol fallback; ambos apuntan a `energy.consumption.recorded`.
- Grupos Kafka duplicados: `KAFKA_CONSUMER_GROUP` y `KAFKA_GROUP_ID` son equivalentes; el código usa el primero y deja el segundo como fallback.
- Variables Kafka existentes pero no usadas por la app runtime: `KAFKA_CLIENT_ID`, `KAFKA_TOPIC_ALERT_SENT`, `KAFKA_TOPIC_PAYMENT_COMPLETED`, `KAFKA_SECURITY_PROTOCOL`, `KAFKA_SASL_MECHANISM`, `KAFKA_USERNAME`, `KAFKA_PASSWORD`.
- `KAFKA_TOPICS` y `KAFKA_BOOTSTRAP_SERVER` solo sirven al init de Docker; no afectan al runtime del microservicio.
- Docker Compose autocrea muchos topics adicionales, pero el consumidor real local de este micro solo queda configurado para 3 topics.
- No encontré consumers sin handler, publishers definidos sin uso, endpoints definidos fuera del router, ni handlers creados pero no conectados.
