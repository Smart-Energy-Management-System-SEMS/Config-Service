1. Nombre del microservicio:  
`Microservice-Energy-Monitoring-Service`

2. Bounded Context al que pertenece:  
`Monitoring` (Energy Monitoring dentro de SEMS)

3. Puerto local usado:  
`8001` (`APP_PORT=8001`)

4. Base URL local:  
`http://localhost:8001`

5. Base URL esperada para deploy:  
No está definida explícitamente en el repo.  
Recomendado registrar como plantilla en Config Service:  
`https://{host-o-gateway}/energy-monitoring` (o el route name que use su API Gateway)

6. Endpoints principales expuestos al API Gateway:  
- `GET /api/v1/energy/health`
- `POST /api/v1/energy-readings`
- `GET /api/v1/energy-readings/user/{user_id}`
- `GET /api/v1/energy-readings/range`

7. Prefijo base de rutas:  
`/api/v1`

8. Variables de entorno necesarias:  
- `MONGODB_URL`
- `MONGODB_DATABASE`
- `KAFKA_BOOTSTRAP_SERVERS`
- `KAFKA_GROUP_ID`
- `KAFKA_TOPIC_READING_INGEST`
- `KAFKA_TOPIC_ANOMALY_DETECTED`
- `KAFKA_TOPIC_ALERT_CREATED`
- `KAFKA_TOPIC_READING_PROCESSED`
- `APP_HOST`
- `APP_PORT`
- `APP_ENV`

9. Variables que son secretas y NO deben exponerse desde el Config Service:  
- `MONGODB_URL` (contiene credenciales/host sensible)

10. Configuración Kafka usada:  
- bootstrap servers: `KAFKA_BOOTSTRAP_SERVERS` (local default `localhost:9092`; en docker interno usan `kafka:9092`)
- security protocol: no configurado en código (implícito `PLAINTEXT`)
- SASL mechanism: no configurado
- topics que produce:
  - `KAFKA_TOPIC_ALERT_CREATED` (`monitoring.alert.created`)
  - `KAFKA_TOPIC_READING_PROCESSED` (`monitoring.reading.processed`)
- topics que consume:
  - `KAFKA_TOPIC_READING_INGEST` (`monitoring.reading.ingest`)
  - `KAFKA_TOPIC_ANOMALY_DETECTED` (`analytics.anomaly.detected`)
- consumer group:
  - `KAFKA_GROUP_ID` (`energy-monitoring-group`)

11. Servicios externos que usa:  
- Apache Kafka broker
- MongoDB (Atlas o local)
- Zookeeper (solo en docker-compose local para Kafka)

12. Base de datos usada:  
- motor: sí (`motor.motor_asyncio.AsyncIOMotorClient`)
- nombre de base de datos: `MONGODB_DATABASE` (default `energy_monitoring_db`)
- variables de conexión:
  - `MONGODB_URL`
  - `MONGODB_DATABASE`

13. Dependencias de otros microservicios:  
- Dependencia asíncrona vía eventos de Analytics Service:
  - consume `analytics.anomaly.detected`
- Dependencia asíncrona vía eventos de IoT/Gateway:
  - consume `monitoring.reading.ingest`
- No se observan llamadas HTTP directas a otros microservicios en este repo.

14. Configuración que actualmente se repite y debería moverse al Config Service:  
- `APP_HOST`, `APP_PORT`, `APP_ENV`
- Todo el bloque Kafka (`bootstrap`, `group`, topic names)
- `MONGODB_DATABASE`
- Convenciones de routing/base path (`/api/v1`)
- Metadatos de servicio (nombre, puerto, URL interna/externa)

15. Recomendación final de cómo debería registrarse este microservicio en el Config Service:  
Registrar un bloque `energy-monitoring-service` con:
- `serviceName`, `boundedContext`, `version`
- `localPort=8001`, `basePath=/api/v1`
- `internalUrl` (ej. `http://energy-monitoring-service:8001`)
- `publicRoute` en API Gateway (ej. `/energy-monitoring/**`)
- `kafka`:
  - `bootstrapServers`
  - `groupId`
  - `topics.produce[]`
  - `topics.consume[]`
  - `securityProtocol` (default `PLAINTEXT`, parametrizable)
- `mongodb`:
  - `databaseName`
  - `connectionUri` referenciada como secreto (no en config público)

Separar en dos capas:
- Config pública/versionable: puertos, rutas, nombres de tópicos, DB name.
- Secretos: `MONGODB_URL` (y futuros secretos Kafka si activan SASL/SSL).
